## 2. Contenido mínimo del documento

- [ ] Portada institucional.
- [ ] Índice.
- [ ] Introducción y contexto.
- [ ] Planteamiento delimitado del problema.
- [ ] Justificación.
- [ ] Objetivo general y objetivos específicos.
- [ ] Alcance y exclusiones.
- [ ] Actores y stakeholders.
- [ ] Al menos 10 requisitos funcionales.
- [ ] Al menos 5 requisitos no funcionales.
- [ ] Diagrama de casos de uso.

- [ ] Flujos principales de usuario.
- [ ] Sistema de diseño.
- [ ] Prototipo desktop y mobile.
- [ ] Estados de éxito, error, vacío y carga.
- [ ] Conclusiones.
- [ ] Referencias bibliográficas.
- [ ] Anexos y evidencias.

## 3. Verificación del enlace Figma

Abrir el enlace en una ventana privada o con una cuenta externa y comprobar:

- [ ] El archivo o prototipo es accesible sin solicitar permisos.
- [ ] La navegación no contiene enlaces rotos.
- [ ] Se puede completar el flujo principal.
- [ ] Se incluyen pantallas desktop de referencia.
- [ ] Se incluyen pantallas mobile de referencia.
- [ ] Los componentes son reutilizables.
- [ ] Existen variantes y estados.
- [ ] Se utiliza Auto Layout donde corresponde.
- [ ] Los textos son legibles.
- [ ] Los contrastes son adecuados.
- [ ] Los botones tienen estados claros.
- [ ] Se muestran errores, carga, vacío y confirmación.

## 4. Verificación del repositorio

- [ ] El README describe correctamente el estado del proyecto.
- [ ] No se afirma que la aplicación esté implementada si solo existe documentación.
- [ ] Los documentos tienen nombres claros y consistentes.
- [ ] No existen enlaces internos rotos.
- [ ] Los requisitos usan códigos únicos.
- [ ] Los diagramas corresponden a la versión actual de los requisitos.
- [ ] Las funcionalidades futuras están identificadas como propuestas.
- [ ] Las métricas no comprobadas están marcadas como objetivos.

## 5. Preparación de la defensa

El equipo debe poder responder:

1. ¿Qué problema concreto se pretende resolver?
2. ¿Quiénes son los usuarios principales?
3. ¿Por qué se necesita una experiencia conversacional?
4. ¿Por qué la solución es offline-first y no simplemente online?
5. ¿Qué funciones forman parte del MVP?
6. ¿Qué funciones fueron excluidas y por qué?
7. ¿Cómo se evita registrar una venta incorrecta interpretada por voz?
8. ¿Cómo se protege la información local?
9. ¿Qué ocurre cuando vuelve la conexión a Internet?
10. ¿Qué elementos están diseñados y cuáles todavía no están implementados?

## 6. Evidencias que no deben inventarse

No presentar como resultados comprobados, si todavía no existen pruebas:

- Porcentaje de precisión del reconocimiento de voz.
- Tiempo real de respuesta.
- Consumo de memoria.
- Resultados de pruebas de usabilidad.
- Porcentaje de reducción de errores.
- Disponibilidad del backend.
- Éxito de sincronización.

Cuando una evidencia no exista, utilizar la etiqueta **[POR COMPLETAR]** o indicar expresamente: **Pendiente de validación mediante pruebas**.
